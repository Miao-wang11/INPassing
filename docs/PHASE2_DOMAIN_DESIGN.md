# 顺手阶段 2：校园 C2C 统一身份与交易规则（设计基线）

状态：2026-10-20，第一批统一身份编码与测试见 `StudentAcceptanceProfileService`，**本文件其余条目是后续开发规范，不代表均已实现**。

## 用户身份（已开始落地）

- 唯一 `user.id`：任何已认证学生既可作为 `task.publisher_id` 发起者，也可作为 `task_order.runner_id` 接单者。
- 管理员是**系统权限**，发布者/接单者是**订单角色**；不建立互斥的“商家账号”。
- `runner_profile` 暂时保留作为历史订单、评分、信用分、在线状态、接单容量的附表，绝不代表第二账户。
- 已认证且未禁用、从未接单的学生点击任务广场“接单”：后端在当前接单事务中原子初始化辅助档案，默认在线；同一学生不需“先申请跑腿员并等待二次审核”。
- **已有档案**：沿用历史审核/在线/封禁/信用与容量规则；不能自动抹去拒绝、人工封禁或主动离线。管理员审核 UI 的历史兼容逻辑待后续阶段整体迁移。
- 禁止自接单、未认证接单、禁用账户接单。用户 ID 从服务器认证上下文取得，不接受前端传入接单用户 ID。
- 与现有 TaskOrderServiceImpl 一起工作：MySQL 任务状态 CAS + Redis 辅助锁；profile 唯一键 `uk_user_id` 防止同时创建多档案。

## 两种信息发布模式（方案，待实现）

### 需求模式：任务（发布后等待别人承接）
发布者 `user.id` → `task.id` → 接单者 `user.id` → `task_order.id`。只有接单后能访问隐私信息。

### 供给模式：服务橱窗（发布“我能帮忙”服务）
服务提供方 `service_offer.provider_id` 创建可展示服务卡，需求方下单生成 `service_invitation`；
双方确认后转为统一的 `task_order`（新建关联 `task`，source=SERVICE，origin_id 指向邀请），**绝不另建一套不兼容的服务订单状态**。

## 订单与支付状态机（设计，尚未完整实现）

- 任务：草稿 → 待展示审核 → 待接单 → 已匹配 → 履约中 → 待确认 → 已完成；取消/过期必须有独立终态；不能靠前端修改状态绕过服务端规则。
- 履约订单：待取货 → 取货完成/执行中 → 待确认 → 已完成；取消和申诉有明确分支。
- 支付：未支付 → 模拟支付成功/冻结 → 可结算 → 已结算；取消、纠纷、部分退款、补差各自独立流水状态。
- 总价 = 服务报酬 + 预估采购成本；结算时跑腿服务收入只含服务报酬，采购实际支出独立记录并留凭证，不能把总价当跑腿报酬。
- 售后判定不能只靠订单是否“已完成”；争议中的款项不应被定时自动结算。

## 首个交付验收项

- 认证通过学生首次抢单无需手动申请双重账号；SQL 默认创建档案并保证唯一。
- 原已封禁、低信用、主动离线者必须保持受限；未认证、被禁、自己发布的订单不可抢。
- 并发抢单最终依赖 MySQL 条件更新，数据库层不得出现多位成功接单人。
- Vue / uni-app 任务广场应该对所有合格学生展示“接单”，而不是“申请成为配送员”。
- 经过单元测试、Maven CI、Docker 容器重启/登录检查；新增真实 HTTP + MySQL 端到端测试，验证两个学生互换发单/接单角色、自接单及重复接单拒绝、已有封禁保留。完整多线程压测另作验收。
