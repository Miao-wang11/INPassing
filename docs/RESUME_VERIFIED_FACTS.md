# ShunShou · 简历可验证事实（仅基于已合并、通过真实 CI 的代码）

## 项目定位

面向校园学生的 C2C 互助交易平台，基于 iRun 作为代码底座进行差异化二次开发。**一个用户账号既可发布需求，也可提供服务和接单**；前端含 Uni-app 用户界面和 Vue3 后台，Java 21 + Spring Boot + MyBatis-Plus + MySQL + Redis + Redisson，Docker Compose 部署。这是一套真实运行的*模拟支付项目*，不得暗示具有微信/支付宝真实结算资质。

## 可陈述的本人实现（须根据 Git commit 归属核实）

1. 校区身份可信绑定：用户提交校区后由管理员审核，业务使用 approved campusId；大厅、搜索、附近、详情与接单由服务端校区约束，不采信前端 campusId。
2. 高并发任务接单：Redisson per-task 分布式锁协调，MySQL compare-and-set 状态条件更新作为权威保证；学生接单容量通过数据库原子更新；已实现并发回归，不虚构 TPS 或吞吐量。
3. 双向服务橱窗：服务者发布报价及有效时间段，委托者主动预约，同一事务内模拟预付、定向任务分配和订单创建；`UNIQUE(requester_id,request_key)` 防重复扣款。
4. 模拟资金闭环：预付金额分为服务费与预估采购报销，账单流水与幂等键记录；未结算售后申请冻结手动/自动确认，由超级管理员仲裁模拟全额退款或驳回。
5. 订单隐私与越权：预约任务及订单仅参与方可查看，陌生学生不可能靠猜 taskId/orderId 获取敏感信息；鉴权在后端而不仅前端隐藏。
6. 线上检查机制：GitHub Actions 构建 Maven、Vue 管理端、Uni-app 关键页面静态语法，运行完整 Docker/MySQL/Redis/Nginx 及业务 HTTP 回归测试。

## 面试讲解建议

**为什么既用 Redis 锁也用数据库条件更新？** 分布式锁提升常态协调效率，但锁过期、事务边界及其他路径写入可能造成并发覆盖；MySQL WHERE 旧状态条件更新、受事务保护的钱包账本才是最终一致性保证。

**为什么用户 campus 文本不能当权限？** 历史字段存放的是学院名称且用户可编辑；必须分离待审字段与管理员确认的校区 ID；任务发布时快照并在查询/接单服务端重新核对。

**怎样避免重复扣款？** 唯一的业务 requestKey 防重复委托，资金转账还有按 taskId 定义的幂等键；都落 MySQL 唯一约束，前端防抖不是资金安全保证。

**怎样处理超时确认与售后申请竞态？** 同一个 taskId 锁协调，业务冻结检查和订单状态条件更新阻止争议期间继续结算；后台仅允许角色 1 在符合条件的订单上做一次终态仲裁，退款与审计同一事务提交。

**流水为什么分服务费与商品预算？** 采购预算本质是垫款报销，不能算作劳动收入或平台营收；两条流水便于退款、对账和未来差价核验。

## 必须诚实说明的边界

此仓库不是成熟支付托管系统：不支持真实微信/支付宝支付、余额与真实银行流水对账、不支持部分赔付或已结算后的追回；移动 Uni-app 页面主要完成了语法检查，未获得全平台真机验收；对大量用户的真实压测结果目前不存在，不能在简历中写“支持十万 QPS”或虚构提升值。
